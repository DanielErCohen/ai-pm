Four skills: challenge a plan, have a doc read by AI stand-ins for the people who will receive it, turn a ticket into an issue, and write in your own voice.

product-sparringSample reply

Position

Do not run a fourth sprint of prompt fixes. Three sprints gave no lift on supplier names and revision tags, so a fourth buys the same result.

Strongest counter

The easy drawings did improve. Shipping those covers part of the job. An estimator still needs the full scope, so a partial read leaves the hard part to a person.

Kill test

This week, run the eval set end to end on one real drawing set. Stop the extraction work if recall stays under the 95% line.

What the plan leaves out

The current approach misses context spread across drawings. Test a change to how the system reads them.

Recommendation

Stop prompting, run the end-to-end test and decide on its result.

Teaching example combining separate events in Parapet's history. The 95% rule was set in September, after the earlier prompt-only rounds.

What you get

  • product-sparring challenges a plan, PRD, metric or go/no-go claim as a peer product lead and gives the strongest counter. It finds the weak part of a plan before you build it.
  • recipient-panel has AI stand-ins for the people who will receive your work read it before you send it. You name the roles. Claude starts one subagent per role. A subagent is a separate AI helper, and at most four run at a time. Each reads the work cold. Every reader reports where they stop reading, their objections with the line each rests on, one fix each, what would make them say yes and a score from 1 to 10. Claude merges the reports, fixes the objections that two or more readers raised first, and tightens the draft.
    • Stakeholder doc: the sponsor who decides, the engineering lead, design, finance or legal, the team that does the work.
    • CV or application: a recruiter screen, HR, the PMs who interview you and the hiring manager. The applicant-tracking check stays a separate formatting check.
    • Product, feature or onboarding: three personas from your exact target segment plus one skeptic (four in total, one batch), each with a job to do, a context and a reason to quit.
    • Public page or post: the target reader, a skeptic, a copy editor and a voice check.
    The output is a simulation. It does not show demand, and you check every fact a reader states. Download the zip or see the skill on GitHub.
  • distill-to-gh-issue turns one finding, bug report or feedback row into a draft issue with the user problem, desired behavior and open decisions for you to review before filing. Claude Code only: it needs the GitHub command line (gh) and a local copy of the repository.
  • voice drafts emails and posts in your voice from rules extracted from your own sent writing, so you make fewer edits. Use writing you own. Check your employer's policy before you paste work email into an AI tool.

  2. To copy recipient-panel alone, run [ -d ~/how-i-work ] || git clone https://github.com/DanielErCohen/how-i-work.git ~/how-i-work && mkdir -p ~/.claude/skills && cp -R ~/how-i-work/skills/recipient-panel ~/.claude/skills/. It works from any folder. Nothing else to configure (2 minutes).
  3. Try product-sparring

First prompt
Use product-sparring to challenge this plan. Ask for any missing product stage or goal. Give your position, the strongest counterargument and the cheapest test that could change the decision.

Plan: [paste your plan]
Evidence: [paste the evidence you have]

Expected result: a reasoned position, a fair counterargument and a test with a decision threshold; check the cited evidence against your inputs.

Try recipient-panel

Paste only what your employer allows. Remove names and customer details first.

First prompt
Use recipient-panel on this doc. Preset: stakeholder doc. The readers are: [role 1], [role 2], [role 3]. They have to decide: [what the doc asks of them]. Merge the reports, fix the objections that two or more readers raised first, and give me a tightened draft.

Document: [paste it]

Expected result: one report per reader, a merged list of objections ordered by how many readers raised them, and a tightened draft. The readers are a simulation. Check any fact a reader states, and use the scores only to compare drafts.

No subagents? One new chat per reader
You are [role: for example the finance lead who approves the budget]. You must [what they decide or do with this doc]. You already know [their context]. You have [their patience, for example two minutes]. You say no when [their reasons].

Read the document below once, as this person. Then reply in under 300 words:
1. The line where you would stop reading, quoted.
2. Up to five objections, each with the line it rests on and one fix.
3. What would make you say yes.
4. One thing that works.

Document: [paste it]

Open a new chat for each reader, then paste all the answers into one chat and ask it to merge the objections two or more readers share.

Try distill-to-gh-issue

First prompt
Use distill-to-gh-issue to draft one issue from this feedback. Ask for the target repository and any missing context. Keep it as a draft for my review.

Feedback: [paste one finding]

Expected result: a draft with the user problem, desired behavior and open decisions; review it before approving publication.

Try voice

First prompt
Use the voice skill to rewrite this draft using my attached voice file. Preserve the facts.

Draft: [paste your text]

Expected result: a revised draft using your writing rules; compare it with the original for changed facts and phrasing you would not use.

Why I use it

Each skill removes one repeated piece of work. product-sparring runs before I build, so a weak plan costs me a conversation. Found after the build, it costs a sprint (a short block of work with one goal). recipient-panel runs before a doc goes out, so likely objections reach me before the real readers see it. distill-to-gh-issue means a raw ticket becomes work an engineer can pick up cold. The voice skill is built from my sent writing and carries a self-check and a slop hook (a small script that runs on its own and flags weak wording) for what the rules miss.

The local config on distill-to-gh-issue lists the orgs it must never file into, because an issue in the wrong org reaches another person.

Came from

  • Sparktale (live)
  • Wellness Coach (work in progress)
  • Parapet (discontinued)

Most of my output on Sparktale is GitHub issues and written decisions for a partner developer who leads engineering, which is what distill-to-gh-issue serves. product-sparring grew from the red team (a fresh Claude session that challenges a plan) that every plan gets in Wellness Coach and the kill tests I wrote for Parapet. The voice skill came from the volume of writing the products ask for.
